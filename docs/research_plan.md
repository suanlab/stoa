# Part I. 선행 연구조사 (Focused Related Work)

## 1. 문제의 지형: 하나의 결정, 세 커뮤니티의 분할

에이전트 메모리에서 각 항목에 대한 근본 결정은 **"무엇을(표현) — 어디에(계층) — 언제(시점) 둘 것인가"** 이다.
현재 연구는 이 셋을 **세 커뮤니티가 한 축씩만** 풀고 나머지를 상수로 고정한다. 아래 §2–§6은 각 축의 최전선을
비판적으로 정리하고, §7은 STOA가 채우는 공백을 위치짓기(positioning) 매트릭스로 종합한다.

핵심 명제: **세 축은 독립 최적화가 불가능한 결합 문제다.** 항목을 잠재/파라미터 표현(M+, MemoryLLM)으로
승격하면 오프라인 비용은 크지만 이후 서빙이 싸고 빠르다; 디스크 평문으로 두면 쓰기는 싸나 읽기가 느리고 토큰을
많이 쓴다. 표현 선택이 계층·시점의 최적값을 바꾸므로, 세 축은 **하나의 예산제약 스케줄링 문제**로만 올바르게
풀린다. ML-for-systems(§5)는 이런 결합 결정이 학습 가능함을 반복 입증했다.

## 6. 신용 할당과 오프라인 통합: 지연 보상 문제의 도구들

배치의 보상은 질의 시점에 **여러 스텝 뒤** 도착하고, 메모리 편집이 궤적 프리픽스를 파열시킨다. 관련 도구:

- **RAG-Gym** (2502.13957) — 단계별 **프로세스 감독**(중첩 MDP), 전이 가능한 critic. → 조밀 보상 근거.
- **PARROT** (2006.16239) — Belady 하인드사이트 최적 배치. → 웜스타트 라벨.
- **DCPO / Memory-as-Action** (2510.12635) — 편집 유발 **세그먼트 수준 advantage**. → 파열 궤적 신용.
- **Sleep-time Compute** (2504.13171) — 질의 전 오프라인 사고로 test-time ~5× 절감. → 시점(오프라인) 축의 가치.
- **LightMem** (2510.18866) — 감각/단기/장기 3단 + 수면기 통합. → 오프라인 통합의 구현 참조.

**공통 한계**: 위 방법들은 각각 검색(Search-R1 2503.09516) 또는 내용 편집에 대한 신용만 다루며,
**표현×계층×시점 결합 행동에 대한 신용 할당은 미해결**이다(survey §8 Gap #4).

## 9. 문제 정형화 (예산제약 MDP)

### 9.1 상태 s_t (후보 항목 i별 특징 벡터)
- **의미(semantic)**: 임베딩 e_i∈ℝ^d, 최신성 recency, 접근빈도 access_freq, 버전/provenance(MemCube 메타),
  예측 미래접근 `predicted_next_access`(PARROT식 Belady 타깃).
- **시스템(systems)**: 현재 표현 ∈ Representation, 현재 계층 ∈ Tier, 크기 size_bytes, 계층별 점유·압력.
- **예산(budget)**: 잔여 지연 여유, 세션 잔여 달러·토큰.
- **질의 문맥**: 현재/예측 질의 임베딩.

→ 코드 대응: `environment.ItemState`, `Budget`. 배치는 메모리 그래프(노드=항목, 엣지=공동접근/엔티티)로 인코딩.

### 9.2 행동 공간 (항목별) — 마스킹 후 **50개**
```
A = 표현 {평문, 벡터, 그래프, 잠재-활성화, 파라미터}   (5)
  × 계층 {GPU, CPU, 디스크, 원격-RDMA}                 (4)
  × 시점 {온라인, 수면기(sleep), no-op}                (3)
```
전체 5×4×3=60. 불법 조합 마스킹(`Action.is_legal`):
- 파라미터 승격은 **수면기 전용**(온라인 금지) → −4
- 잠재(KV) 메모리는 **GPU/CPU 전용**(디스크/RDMA 금지) → −6

→ **합법 행동 = 60 − 4 − 6 = 50** (두 집합은 서로소; `Action.space()` 반환 크기와 일치).
조합폭발 완화: 공유 트렁크 위 **π_θ = π_rep · π_tier · π_time 분해** + 배치 GNN 결정(Decima식).

### 9.3 보상·목적 (라그랑주 완화)
```
max_θ  E[ Σ_t U(a_t) ]   s.t.  Latency ≤ L,  Cost($) ≤ C,  Tokens ≤ B
r_t = U − λ_L·lat − λ_C·cost − λ_B·tok + freshness_bonus
```
U = 다운스트림 태스크 보상(정답 정확도 또는 RAG-Gym식 프로세스 보상). λ_L,λ_C,λ_B는 학습형 듀얼.
운영자가 서빙 시 (L,C,B)를 설정 → 정책이 적응하는 **단일 제어 노브**. → 코드 대응: `environment.reward`,
`RewardWeights`, `configs/default.yaml`.

## 10. 제안 방법 / 아키텍처

MemOS식 저장소 + LMCache식 계층화 + M+식 잠재경로 위의 **제어 평면**(`orchestrator.Orchestrator`).

1. **지각(GNN)** — 메모리 그래프 + 시스템 텔레메트리를 인코딩 → 항목별 임베딩(`policy._encode`).
2. **정책(factored actor)** — 항목별 (표현, 계층, 시점) 방출 + 합법성 마스킹; critic이 제약 가치 추정.
   별도 admission/consolidation 헤드가 수면기 큐 항목 선택.
3. **실행** — 온라인: MemCube migrate/fuse + LMCache put/get; 오프라인: 유휴 구간에 평문→잠재/파라미터 승격,
   그래프 요약 통합(LightMem식).

**신용 할당 파이프라인**(§6 도구 결합, `credit.py`):
Belady 웜스타트(`belady_optimal_tier`) → 프로세스 감독 critic(RAG-Gym) → 세그먼트 advantage(DCPO).
**학습 순서**: 오프라인-RL 우선(Cold-RL식, 로그에서 안전) → 가드된 온라인 GRPO.

- 정적 MemOS(고정 계층) · LMCache-only(시스템만 계층화) · Sleep-time/LightMem(전역 오프라인).
- 휴리스틱 축출: LRU · 중요도/H2O(2306.14048) · Attention-Gate(2410.12876) 학습 축출.
- 학습형(내용만): Memory-R1(2508.19828).

### 11.3 RQ ↔ 실험 매핑 (핵심 표)
| 실험 | 조작 변수 | 비교 대상 | 측정 | 답하는 RQ |
|---|---|---|---|---|
| E1 축별 ablation | {계층만, 표현만, 시점만, 공동} | 휴리스틱 4종 | Pareto HV | RQ1 |
| E2 예산 스윕 | B∈{2k,4k,8k,16k}, L∈{100,500,2000}ms | 정적 MemOS | 프론티어 형태 | RQ1, RQ3 |
| E3 웜스타트 vs from-scratch | {Belady+프로세스, outcome-only} | Belady 오라클 | 오라클 격차, 샘플효율 | RQ2 |
| E4 예산조건 전이 | 미학습 (L,C,B) 5점 | 각 점 전용학습 정책 | 제약 위반율, 정확도 | RQ3 |
| E5 백본 전이 | 백본 A→B 무재학습 | B 재학습 정책 | 정확도 손실 | RQ3 |
| E6 sim-to-real | 시뮬 vs 실 vLLM+LMCache | — | 지연·비용 예측오차 | 타당성 |

각 실험 **≥5 시드**, 신뢰구간 보고. 축별 ablation으로 각 축의 한계기여를 분리한다.

## 12. 평가 프로토콜

- **지표 정의**: 정확도(벤치별 공식 metric); end-to-end 지연(TTFT+총); \$/질의·토큰/질의;
  **신선도** = 지식갱신 하 stale 응답 비율(LongMemEval 갱신·기권 하위셋); 통합 오버헤드(오프라인 GPU-시간).
- **파레토 hypervolume**: (정확도↑, 지연↓, 비용↓) 3D에서 공통 기준점(nadir) 대비 지배 부피. 기준점은
  전 방법 최악값으로 고정, 방법 간 동일 좌표계.
- **통계**: 시드 간 부트스트랩 CI(95%), 방법 쌍 비교는 paired test + 다중비교 보정.
- **재현성**: 고정 시드·config 스냅샷·트레이스 해시 기록. `experiments/`에 산출물 로깅(모델 가중치는 VCS 제외).
- **안전 지표**: LongMemEval 기권(abstention)을 통합 손상 여부의 안전 지표로 사용; 통합이 사실을 훼손하면
  기권/오답률로 드러남.

## 13. 데이터·시뮬레이터 계획 (M0–3 핵심)

1. **트레이스 수집**: LMCache식 KV 접근 로그 + MemOS/M+ 잠재경로 계측 → (접근시각, 항목, 계층, 크기) 튜플.
2. **시뮬레이터 보정**: `simulator.py`의 계층별 지연(`_TIER_READ_MS`)·표현별 토큰(`_REPR_TOKENS`)·승격비용
   (`_PROMOTE_COST`)의 **현재 placeholder 값을 실측 트레이스로 회귀 적합**. 수면기=오프라인 amortize,
   no-op=무비용 경제학 유지.
3. **오라클 라벨 생성**: `credit.belady_optimal_tier`로 재사용거리 기반 사후최적 계층 라벨 → 오프라인 데이터셋.
4. **검증(E6)**: 상위 정책은 시뮬레이터에서 학습하되, 실 vLLM+LMCache에서 지연·비용 예측오차를 측정해
   sim-to-real 격차를 정량화(목표: 지연 예측 상대오차 ≤15%).

## 부록 C. 진행 로그 (실측)
- **M0–3** (`scripts/build_dataset.py`): 오프라인 데이터셋 + 오라클 상한. 재현성 게이트 통과(동일 시드→동일 산출물).
  - 정적 배치(64 items, seed 0): 오라클상한 20.3 ≤ 그리디 151.2 ≤ 나이브 600.0; 그리디가 나이브 대비 −74.8%.
- **M3–6** (`scripts/run_ablation.py`): 축별 ablation(E1). **Go 게이트 통과**(계층 컨트롤러≥휴리스틱).
  - 계층축(온라인, zipf 1.1): **Belady > H2O > LRU**, 오라클 갭 캐시 0.05→0.20에서 +3.5→+6.7pp.
  - 표현/결합축(정적): 그리디가 나이브 대비 토큰비용 −73%. 오라클 갭이 학습 컨트롤러(RQ2)의 목표.
  - 미완: LongMemEval/LoCoMo 실 어댑터(`datasets` 필요), 실 트레이스 시뮬레이터 보정.
- **M6–9 torch-free 코어** (`scripts/train_controller.py`): 학습형 계층 컨트롤러(RQ2).
  - 선형 Belady-모방 예측기(PARROT식)를 트레이닝 트레이스에 적합 → 홀드아웃 평가.
  - **정상 Zipf(β=0)**: H2O가 이미 오라클 근접 → 학습 이득 없음(무기억성; 정직한 음성 결과).
  - **시간적 지역성(β=0.5)**: 학습 컨트롤러 70.8% > LRU 69.3% > H2O 64.6%(홀드아웃 평균),
    오라클(78.4%) 갭의 ~16% 회수. 나머지 ~84%는 M6–9 GNN+오프라인-RL의 몫(torch 필요).
  - 함의: 인구빈도(LFU)와 최근성(LRU)이 공존할 때만 학습형이 두 휴리스틱을 동시 지배.
- **M9–12 torch-free 코어** (`scripts/run_budget_frontier.py`): 예산조건 제어(RQ3).
  - 단일 노브 B → 최소비용 실현가능 배치. 프론티어 단조: B 6.4M→0에서 $0→$0.32, 승격 0→64.
  - **RQ3 제어성**: 타이트 예산(B=320k)에서 all-plaintext(6.4M tok)는 위반, 제어기는 충족($0.06).
    정적 정책은 단일 점(한 예산에만 최적) → 노브가 전 구간 적응.
  - **RQ1 정직한 한계**: placeholder 비용에서 vector 승격이 저렴($0.00025/680n tok) → uniform-vector가
    이미 효율적이라 파레토 지배 폭 작음. 실 트레이스 보정(M0–3) 후 재검 필요.

- **M6–9 GNN 분해 정책** (`scripts/train_gnn_policy.py`, torch **CPU**): Belady 행동복제 웜스타트(RQ2).
  - `gnn.py`: GCN 트렁크 + π_rep·π_tier·π_time 팩터 헤드 → 50개 합법행동 마스킹 소프트맥스 + value 헤드.
  - `train.py`: 공동접근 그래프 + 노드특징 + Belady 그리디 라벨 → BC. 홀드아웃(seed 0–4) 평가.
  - **결과**: 학습정확도 93%, 홀드아웃 모방정확도 ~87%, BC 비용이 Belady 타깃의 −11%~+10%(평균 하회),
    naive→타깃 갭 ~104% 회수. **GPU 불필요**(시뮬레이터 위 학습).

- **LLM 태스크효용 하니스** (`scripts/run_memqa.py`, **GPU 불필요**, LLM은 HTTP API):
  - 지금까지 `reward`의 U를 1.0 상수로 뒀으나, 예산하 QA로 **실 정확도**를 측정하도록 연결.
  - 예산 B 하에서 STOA 열(heat=접근빈도) 기반 팩트 선택 vs 무작위 선택 → 정확도-예산 프론티어.
  - **실 LLM 실측**(gpt-4o-mini, facts=30/Q=40): STOA가 무작위 대비 예산 30/60/120 tok에서
    **+22.5/+25.0/+25.0pp**, 180 tok(전량)서 수렴(100%). → `experiments/eval_memqa.json`.
  - 정직한 한계: 이 QA는 단순 조회라 gpt-4o-mini가 in-context 문항을 100% 맞힘(정확도=in-context율).
    LLM 자체 U<1을 자극하려면 distractor·다중홉을 추가해야 함(다음 증분).
  - **보안**: API 키는 `$OPENAI_API_KEY` 환경변수에서만 읽음(코드·커밋에 비밀 없음). 유출 키는 폐기·교체 권장.
- **2-hop QA** (`--multihop`): 링크(A→B)+값(B=v) 체인, distractor 다수. STOA가 무작위 대비 **+52~77pp**
  (2-hop은 연결 팩트 *공동배치*가 필수라 무작위가 거의 실패). 단, gpt-4o-mini의 reason-acc=100%
  → 이 합성 태스크는 배치가 병목이고 모델 추론은 완벽(U<1을 보려면 실 벤치마크 필요).
- **LoCoMo 실 벤치마크** (`eval/locomo`, `scripts/run_locomo.py`): 300턴 다세션 대화(10샘플).
  턴=팩트, evidence=needed 매핑. 예산 30%서 demand-aware 선택이 무작위 대비 answerable **118 vs 41**.
  - **실 LLM 실측**(gpt-4o-mini, sample0, Q=12): 예산 10/25/50%서 STOA **50/58/58%** vs 무작위 **0/0/25%**
    (**+33~58pp**). 전량 예산서 둘 다 **50%** — 실 벤치마크는 팩트가 다 있어도 **U<1**(합성 태스크의
    100%와 대비: 실 데이터가 모델 추론을 실제로 자극). 정답은 substring 근사(공식 F1/judge 아님)라 절대값은 하한.
- **RL 파인튜닝** (`rl`, `scripts/finetune_rl.py`): BC 웜스타트 위 REINFORCE(per-item 신용 + value baseline).
  정직한 결과: BC(그리디 근접)를 정적 배치서 **명확히 지배 못함** — beta↑ 시 실현가능(overflow→0) 유도되나
  비용 프리미엄, 노이즈. 진단: 동시적 per-node 정책엔 계층 점유상태 부재 → 순차 점유인식 MDP가 다음 형식.
- **순차 점유인식 MDP** (`sequential`, `scripts/train_sequential.py`) — 위 음성 결과의 **해소**:
  항목을 heat 순으로 순차 배치, 정책이 실시간 계층 점유를 관찰하고 여유 있는 계층만 마스킹 선택
  (구성상 항상 실현가능). REINFORCE(return-to-go + value baseline)로 학습 → **sequential-RL이 그리디-Belady
  오라클 비용(853) 도달** + 전 트레이스 실현가능. 대비: random-feasible 5725(6.7× 나쁨), static BC 868이나
  1/3서 용량 위반. **결론: 부족했던 건 더 많은 RL이 아니라 점유 상태였음.**
- ~~**LoCoMo 최종(LLM-judge × 3대화)**: STOA vs 무작위 +29~50pp~~ → **⚠️ 무효 (테스트셋 유출)**.
  `demand()`가 **평가 질문의 정답 근거(`q.needed`)** 를 읽어 랭킹을 만들었음 = 오라클. 2026-08-09 발견.
  이전 LoCoMo 수치(`eval_locomo*.json` 중 leak-free 이전 것) 전부 **인용 금지**.
  - **수정**: `split_history()`로 과거(history) 질문에서만 demand 추정 → 미지의 held-out 질문으로 평가.
    `MemQATask.leak_free` 속성 + `tests/test_leakage.py`로 회귀 방지. `strict=True`는 반복 질문까지 제거해
    **미지 질문 일반화**를 측정(반복 재접근을 모델링하려면 `strict=False`, 단 그렇게 보고할 것).
  - **베이스라인 보강**(`eval/retrieval.py`): 무작위(허수아비) 대신 **임베딩 centrality**(질의 비인지, 동일 조건)와
    **질의별 top-k 검색**(질의 인지, 실제 RAG 기준선) 추가 — 리뷰어가 반드시 요구할 비교.
  - **유출 제거 후 실측**(`experiments/eval_locomo_leakfree.json`, 3대화):
    예산 10/25/50%에서 **STOA 6.7/13.3/23.3%**, random 3.3/6.7/13.3%, centrality 0/6.7/10%,
    **질의인지 retrieval 36.7/40.0/36.7%**.
    → ① STOA 우위는 **+3~10pp로 축소**(질의 비인지 동급들만 상회), ② **질의 인지 검색이 5배 이상 압도**.
    정직한 해석: **배치(placement) 신호는 검색(retrieval) 신호가 아니다.** 컨텍스트 채우기는 질의 인지가
    지배하며, STOA의 기여(계층·표현 배치=지연·비용 지배)는 그와 **직교**하고 결합해야 함.

- **⚠️ 두 번째 유출: GNN/순차 정책의 입력 특징** (2026-08-09 발견, **미수정**)

  → **§5.3 BC 87%, §5.7 "오라클 도달" 수치는 미래 정보를 본 결과**이므로 그대로 인용 불가.
  - **수정 완료**: `traces.prefix_stats()`/`future_counts()` 신설 → 정책 입력은 관측 prefix(50%) 통계,
    오라클은 미래 접근수로 라벨·비용만 채점. `train`/`sequential`/`rl`/`oracle` 전부 관통.
  - 재측정: BC holdout 86.9→**85.6%**, 갭 회수 103.8→**101.2%**, 순차 RL은 여전히 오라클 도달.

- **⚠️ 근본 진단: 테스트베드가 자명(degenerate)했음** (2026-08-09)
  1. **비용 모델**: 승격비($0.02)가 접근당 토큰비(0.4)보다 압도적으로 싸 `n≥1`인 모든 항목의 최적 행동이
     동일(`latent/gpu/sleep`). 항목별 결정이 사라져 문제가 "접근수 정렬"로 붕괴. (미통과 M0–3 보정 게이트의 직접 결과)
  2. **워크로드**: 정상 Zipf → 과거가 미래를 거의 완벽히 예측. **예측 이득(headroom) 0.7%**.
     → 학습이 오라클과 동률로 나온 것은 실패가 아니라 **여지가 없는 곳에서 측정**한 것.
  3. **측정 버그(정정)**: 초기 headroom 0.00% 보고는 오라클이 prefix 순서를 물려받은 탓. `order_by="future"`로 수정.
  - **비정상 워크로드 도입**(`WorkloadConfig.phase_shifts`): 구간마다 인기 순위 교체 →
    **headroom 44%** 확인. 학습형 캐싱(PARROT·Cold-RL)이 실 트레이스에서 평가되는 이유와 동일한 조건.
  - 함의: **RQ2는 반증된 것이 아니라 미검증**. 유효한 검증은 (a) 비정상 워크로드, (b) 실 트레이스 보정 후에만 가능.

- **🔴 결론: 현 테스트베드에서 RQ2는 원리적으로 검증 불가** (2026-08-09, 다중 프로브로 확증)
  | 워크로드 | corr(과거,미래) | headroom | 학습 결과 |
  |---|---|---|---|
  | 정상 Zipf | 0.996 | 0.7% | 회수 −2.5% (동률) |
  | 비정상(무작위 재배치) | 0.118 | 43% | 회수 −45% (더 나쁨) |
  | 드리프트 0.1~0.3 | 0.77~0.84 | 6~10% | 최근성 순서도 −14~−42% |
  - **구조적 원인 3가지**:
    1. **비용 모델 퇴화** — `n≥1`이면 최적 행동이 항상 동일 → 3축 결정이 **1차원 정렬 문제**로 붕괴.
    2. 정렬이 중요한 건 GPU에 들어가는 **~6개 항목**뿐(64개 중) → 결정 공간이 극히 작음.
    3. 그 6개를 과거로 맞히는 건 **자명하거나(정상: 모두 성공, 여지 0) 불가능**(드리프트/재배치: 아무도 실패).
       중간 지대가 존재하지 않음 — 정렬은 학습 문제가 아니기 때문.
  - **⇒ 블로커는 미통과 M0–3 보정 게이트(실 트레이스/실측 비용)이며, 그 전의 모든 학습 실험은 무의미.**
    RQ2·RQ1의 학습 주장은 보정 이후에만 시도해야 함.
  - 살아남은 기여: 정형화(C1)·아키텍처(C2)·인프라(시뮬레이터·오라클·하니스·LoCoMo 어댑터·검색 베이스라인·
    유출 방지 프로토콜) + **방법론적 negative 결과**(유출 2건 발견·수정, 테스트베드 퇴화 진단).

- **🟢 돌파구: 실 트레이스가 RQ2를 연다** (2026-08-09, `src/stoa/mooncake.py`)
  Mooncake 공개 프로덕션 트레이스(FAST'25, arXiv:2407.00079) 도입 — `hash_ids`=KV 블록 식별자라
  반복 등장이 진짜 재사용. `toolagent_trace`는 **에이전트 워크로드 = STOA의 대상 도메인**. GPU 불필요(4MB).
  | 워크로드 | 항목수 | prefix-greedy | oracle | headroom |
  |---|---|---|---|---|
  | 합성 Zipf(기존) | 64 | 414.9 | 402.3 | **3.0%** |
  | Mooncake conversation | 38,788 | 33,932 | 6,099 | **82.0%** |
  | Mooncake toolagent | 21,548 | 16,894 | 3,313 | **80.4%** |
  - 구조적 차이: 블록의 **78%가 1회만 접근**(합성 ~0%), 최대 재사용 12,031회(공유 프리픽스), 항목 18만 규모.
    → *"이 블록이 재사용될 것인가"* 가 처음으로 **실제 예측 문제**가 됨(PARROT이 푸는 바로 그 문제).
  - **버그 정정**: 초기 측정의 headroom 100%(oracle=0)는 분할점을 `len(accesses)` 기준으로 잡아
    트레이스 끝을 넘어간 탓. `Workload.time_split()`(타임스텝 기준)으로 수정 — 실 트레이스는 1스텝에
    다수 접근이 발생해 두 값이 자릿수만큼 다름.
  - **⇒ 다음 단계(유효)**: BC·순차 정책을 **실 트레이스에서** 재학습해 80% headroom 중 회수율 측정.
    이것이 RQ2의 최초 유효 검증이며, 합성에서의 모든 학습 결과를 대체함.

- **🔬 실 트레이스 RQ2 결과 + 문제 구조 규명** (`scripts/train_on_mooncake.py`, `experiments/mooncake_rq2.json`)
  프로토콜: prefix 특징(count·recency·age·inter-arrival·요청 내 위치) → 미래 접근수 라벨,
  **교차 트레이스**(한 트레이스로 학습, 다른 것으로 평가), 배치는 예측으로 정렬·선택하되 **비용은 실제 미래로 청구**.
  - **결과: 학습이 headroom의 0.4~0.9%만 회수** (26563→26479, 12711→12616).
  - **왜인지 규명 — 문제 구조가 답을 준다** (toolagent, prefix 등장 블록 9,546개):
    | prefix 접근수 | 블록수 | 이후 재사용 확률 | 평균 미래 접근 |
    |---|---|---|---|
    | 1회 | 8,630 | **12.7%** | 0.17 |
    | 2회 | 891 | 19.3% | 0.27 |
    | 21회+ | 18 | **100%** | 257.6 |
    - **이진 오라클**(재사용 *여부*만 알고 횟수는 모름)이 **headroom의 99.7%를 회수**.
      → headroom은 전부 **이진 재사용 판정**에 있고, 횟수 정밀 예측은 거의 무의미.
    - 분포가 **극단적 이봉형**: 18개 공유 프리픽스(100% 예측 가능, 빈도 휴리스틱이 이미 포착)와
      8,630개 1회성 블록(재사용률 12.7%, 블록 자체 이력으로는 거의 예측 불가)로 갈림.
  - **⇒ 결론(핵심 발견)**: 블록-지역 통계만 쓰는 한 **빈도 휴리스틱이 사실상 최적**이고, 남은 80% headroom은
    **더 좋은 모델이 아니라 외생 정보**(세션/대화 활성 여부, 클라이언트 think-time, 요청 수준 문맥)를 요구함.
    KV 블록의 재사용은 "사용자가 그 대화를 이어가는가"라는 **정책 외부 사건**에 지배되기 때문.
  - 후속 실험 설계: Mooncake `timestamp`·kv-cache-tester `think_time` 등 **세션 수준 특징**을 도입해
    이진 재사용 판정의 AUC와 headroom 회수율을 측정. 이것이 RQ2의 올바른 다음 형태.

- **🔴 RQ2 최종 답(현 데이터 기준): 재사용은 트레이스-지역 정보로 유용하게 예측되지 않는다**
  (`scripts/train_session_features.py`, `experiments/mooncake_session_rq2.json`)
  세션 수준 특징 도입(요청의 첫 `hash_id`로 대화 추론 → 세션 최근성·크기·도착률·수명):
  | 프로토콜 | AUC block | AUC +session | headroom 회수 |
  |---|---|---|---|
  | in-trace(동일 트레이스 적합) | 0.601 | **0.639** | — |
  | 교차 트레이스(전이) | 0.44~0.50 | 0.48~0.53 | ~0% |
  | **시간 분할(현실적 배포)** | 0.43~0.58 | 0.50~0.60 | **≈0%** |
  - 세션 특징은 in-trace에서 **+0.038 AUC**로 방향은 옳으나, 전이되지 않고 배치 절감으로 이어지지 않음.
  - **랭킹 개선 ≠ 배치 개선**: AUC 0.60에서도 headroom 회수 −0.1%. 배치는 신념의 *크기*가 승격 임계를
    넘는지에 좌우되며, 약한 랭킹으로는 78%의 1회성 블록을 걸러내지 못함.
  - **⇒ 결론**: headroom(80%)은 실재하고 전부 이진 재사용 판정에 있으나(99.7%), 그 판정은
    **익명화된 KV 트레이스에 남아 있는 정보로는 예측 불가**. 필요한 것은 더 좋은 모델이 아니라
    트레이스에 없는 정보(실제 사용자/세션 지속 행동, 요청 내용, 애플리케이션 문맥).

- **⚠️ 이 라운드에서 발견·수정한 자체 버그 2건** (결과 해석에 직접 영향)
  1. **AUC 동점 처리**: `sorted(zip(scores,labels))`가 label을 부차 정렬키로 써서 동점 그룹 상단에 양성을
     몰아넣음 → `log(count)` AUC가 0.936으로 부풀려짐. 평균 순위(mid-rank)로 수정 후 **실제 0.512**.
     (동점이 수천 개인 카운트 특징에서 특히 치명적)
  2. **로지스틱 미수렴**: 특징 표준화 없이 순수 파이썬 GD → 과소적합. 표준화 + numpy 벡터화로 수정.
  - 교훈: 랭킹 지표는 동점 처리를 명시 검증할 것. 단일 특징이 학습 모델을 이기면 대개 지표 버그.

### 하드웨어 현황 & 자율 진행(/loop) 종료 지점
이 머신: **GPU 없음, CPU 112코어 / RAM 502GB**. STOA 학습은 LLM이 아니라 *시뮬레이터* 위에서 이뤄지므로
M0–12의 학습 연구는 **전부 CPU로 완료**(총 34 테스트 통과, 5개 실측 아티팩트, torch 2.x CPU).
GPU가 실제로 필요한 유일 구간과 대안:
- **오프라인-RL/온라인 GRPO 파인튜닝**: CPU로 가능(다음 증분). value 헤드는 `gnn.py`에 준비됨.
- **`datasets` + LLM API**: LongMemEval·LoCoMo·MemoryAgentBench 실 어댑터(`eval/benchmarks.load`).
  에이전트 응답은 **LLM API로 대체 시 GPU 불필요**.
- **실 vLLM+LMCache 배포(M12–15)**: 유일한 하드 GPU 게이트 → 클라우드 GPU 단기 대여로 트레이스 수집 +
  sim-to-real 검증 후 나머지는 이 CPU 박스로. 또는 공개 LMCache 트레이스로 보정.
- 재개 지점: `gnn.py`/`train.py`(RL 파인튜닝), `eval/benchmarks.py`(어댑터), `simulator.py`(보정).
